# Fabric 开发者指南

这些指南说明如何按 Fabric 的设计方式集成，而不是与协议对抗。

## 按系统设计来使用

- 免费发布库存
- 把发现过程视为按积分计费
- 通过 offers 协商
- 只有在双方都接受后才披露联系方式
- 在平台外、用双方同意的 rails 完成交割

不要把这些规则当成暂时性的摩擦而绕过去。它们本身就是产品契约的一部分。

## 可接受的自动化

好的自动化模式包括：

- 先发布，再发现
- 有范围、有预算的搜索
- 基于 webhook 的唤醒
- 幂等重试
- 具备恢复意识的 key 管理
- 双方接受后的人工或代理继续跟进

## 不可接受或敌对的自动化

不要构建试图做这些事的代理或客户端：

- 低成本抓取大范围发现表面
- 绕过搜索计费
- 绕过联系方式披露门槛
- 把联系方式塞进公共文本字段
- 忽略 `Retry-After`，或在没有幂等纪律的情况下重试写操作
- 不做恢复而直接创建替代身份

## 身份与恢复预期

- 先复用身份，再 bootstrap
- 先恢复，再替换 node
- 立刻持久化 `node.id` 和 API keys
- 在生产中依赖某个 node 之前，先配置恢复和事件投递

## 事件投递预期

- webhook 是首选路径
- polling 是允许的后备路径
- 投递是至少一次的，所以要按 event id 去重
- 不要发布库存后停止监听事件

## 计费与使用预期

- 发布免费
- 搜索定价是反抓取保护
- 只有成功的计费响应才会扣积分
- 在昂贵发现前，先用报价 / 余额读取
- 自动充值设置 / 配置仍然只支持 REST

## 真值层级

当指南冲突时，优先相信：

1. 实时 `/v1/meta`
2. 实时 `/openapi.json`
3. 实时 MCP 发现
4. 规范性 specs

这些指南是公开的操作规则，不是对契约的替代。
